# mlx-audio-io 1.3.12

## MLX version gate is now a verified-version list, not string equality

`mlx-audio-io` previously refused to import unless the runtime MLX version
matched the build-time version exactly. That made it impossible for downstream
projects to evaluate any other MLX release at all — a user investigating
[ssmall256/mlx-audio-separator#4](https://github.com/ssmall256/mlx-audio-separator/issues/4)
reported they "couldn't test other MLX versions because mlx-audio-io pins
`mlx==0.31.2`".

The underlying constraint is real and has not changed: the extension links
`libmlx` directly, passes `mlx::core::array` by value, and shares nanobind's
type registry through `NB_DOMAIN mlx`. MLX has no stable C++ ABI and ships no
soname versioning, so a mismatch is a crash rather than a link error. MLX 0.32.0
is a concrete example — `StreamOrDevice` gained a variant alternative, which
remangles every operation taking a stream, so a binary built against 0.31.x
cannot load against 0.32.x.

What changed is the granularity and the escape hatch:

- The build records **every MLX version it was compiled and tested against**, not
  just the one it happened to build with. Set it at configure time once a version
  is verified:
  `-DMLX_AUDIO_IO_COMPATIBLE_MLX_VERSIONS="0.31.2,0.31.3"`. It defaults to the
  build-time version, so behavior is unchanged unless you opt in.
- The loader accepts any version in that list and rejects the rest, with a
  message naming both the runtime version and the supported set.
- `MLX_AUDIO_IO_ALLOW_MLX_MISMATCH=1` downgrades the rejection to a
  `RuntimeWarning`, so a compatibility investigation no longer requires patching
  the package. Native crashes remain possible; this is not for production.
- `mlx` requirements widen from `==0.31.2` to `>=0.31.2,<0.32` for both the build
  and runtime dependency. A wheel must still stay inside a single MLX minor, and
  a packaging test now enforces that the bound is never dropped or turned back
  into an exact pin.

## Fixed

- `load_build_info()` dropped any build-info field outside a hardcoded key set.
- Editable checkouts reported all build metadata as unknown, because
  `importlib.resources` resolved `mlx_audio_io` to the source tree, which holds
  only `_build_info.json.in`. The generated JSON lives beside the compiled
  `_core` module, and is now read from there as a fallback. This silently
  disabled the MLX version gate in development checkouts — precisely where an
  ABI mismatch is most likely to be encountered.


## MLX 0.32.x support

Verified against **MLX 0.32.2**: the extension rebuilds cleanly and all suites pass
(210 mlx-audio-io, 219 mlx-spectro, 277 mlx-audio-separator, 32 demucs-mlx), with
Demucs output **bit-identical** to 0.31.2 (max abs diff 0.000e+00 across all stems).

Two things had to change, and only one of them was the MLX pin:

- `mlx` widens to `>=0.31.2,<0.33` for both build and runtime. The range describes
  what this source tree can be built against; which MLX a *built* extension can load
  is enforced separately by the build-recorded compatible-version list, which fails
  loudly rather than crashing.
- **`nanobind` widens to `>=2.12.0,<2.16`, and this was the actual blocker.** MLX
  0.31.x builds with nanobind 2.12.0 and MLX 0.32.2 with 2.15.0. Because the
  extension shares nanobind's type registry with `mlx.core` through `NB_DOMAIN`, a
  mismatch compiles and links cleanly and then fails on the first call with
  `Unable to convert function return value to a Python type`. The build now prints
  the MLX/nanobind pair and warns on a known-bad combination.
